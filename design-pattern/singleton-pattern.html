Patrón Singleton

El patrón Singleton (Singleton Pattern) es uno de los patrones de diseño más simples de Java. Este tipo de patrón de diseño pertenece a los patrones de creación y proporciona una de las mejores formas de crear objetos.

Este patrón involucra una única clase que es responsable de crear su propio objeto, al mismo tiempo que asegura que solo se cree un único objeto. Esta clase proporciona una forma de acceder a su objeto único; se puede acceder directamente sin necesidad de instanciar un objeto de esa clase.

El patrón Singleton es un patrón de diseño de creación que asegura que una clase tenga solo una instancia y proporciona un punto de acceso global para acceder a dicha instancia.

Nota:

  • 1. La clase singleton solo puede tener una instancia.
  • 2. La clase singleton debe crear su propia instancia única.
  • 3. La clase singleton debe proporcionar esta instancia a todos los demás objetos.

Resumen

Patrón Singleton (Singleton Pattern)

Intención

Asegurar que una clase tenga solo una instancia y proporcionar un punto de acceso global para acceder a ella.

Problema principal

El problema de crear y destruir con frecuencia instancias de clases utilizadas globalmente.

Cuándo usarlo

Cuando sea necesario controlar el número de instancias y ahorrar recursos del sistema.

Cómo solucionarlo

Verificar si el singleton ya existe en el sistema; si existe, devolver esa instancia; si no existe, crear una nueva instancia.

Código clave

El constructor es privado.

Ejemplos de aplicación

  • Una clase solo tiene un tutor.
  • Cuando Windows opera con archivos en un entorno de múltiples procesos y múltiples hilos, para evitar que varios procesos o hilos manipulen un mismo archivo simultáneamente, es necesario procesarlo a través de una instancia única.
  • El administrador de dispositivos está diseñado con el patrón Singleton. Por ejemplo, si una computadora tiene dos impresoras, se evita que ambas impriman el mismo archivo al mismo tiempo.

Ventajas

  • Hay una sola instancia en la memoria, lo que reduce el gasto de memoria, especialmente cuando se crean y destruyen instancias con frecuencia (como la caché de la página de inicio de la Escuela de Administración).
  • Evitar la ocupación múltiple de recursos (como operaciones de escritura de archivos).

Desventajas

  • No tiene interfaz, por lo que no puede heredarse.
  • Entra en conflicto con el principio de responsabilidad única; una clase debería ocuparse solo de su lógica interna, no de la forma de instanciación.

Escenarios de uso

  • Generar números de secuencia únicos.
  • Contadores en la Web: para evitar que cada actualización incremente el contador en la base de datos, primero se almacena en caché.
  • Crear objetos que consumen demasiados recursos, como I/O y conexiones de base de datos.

Consideraciones

  • Seguridad para hilos：getInstance()En el método se debe utilizar un bloqueo de sincronizaciónsynchronized (Singleton.class)Evitar que múltiples hilos entren simultáneamente y provoquen la creación de la instancia varias veces.
  • Inicialización diferida: la instancia se crea la primera vez que se llamagetInstance()al método.
  • Serialización y deserialización: sobrescribirreadResolveel método para asegurar que no se cree una nueva instancia al deserializar.
  • Ataque por reflexión: agregar código de protección en el constructor para evitar crear nuevas instancias mediante reflexión.
  • Problema del cargador de clases: preste atención a los problemas de múltiples instancias que pueden ser causados por entornos complejos de carga de clases.

Estructura

El patrón Singleton incluye los siguientes roles principales:

  • Clase Singleton: la clase que contiene la instancia singleton; normalmente declara el constructor como privado.
  • Variable miembro estática: variable miembro estática utilizada para almacenar la instancia singleton.
  • Método de obtención de instancia: método estático utilizado para obtener la instancia singleton.
  • Constructor privado: evita que el exterior instancie directamente la clase singleton.
  • Manejo de seguridad para hilos: garantizar que la creación de la instancia singleton sea segura en entornos multihilo.

Varias formas de implementar el patrón Singleton

Hay varias maneras de implementar el patrón Singleton, como se muestra a continuación:

1. Estilo perezoso, no seguro para hilos

¿Inicialización Lazy?:Sí

¿Es seguro para hilos?:no

Dificultad de implementación:fácil

Descripción:Esta es la forma de implementación más básica. El mayor problema de esta implementación es que no admite múltiples hilos. Debido a que no se usa el bloqueo synchronized, en sentido estricto no se considera un patrón Singleton.
En este enfoque, la carga diferida (lazy loading) es evidente; no se requiere seguridad para hilos y no puede funcionar correctamente en entornos multihilo.

Ejemplo

public class Singleton { private static Singleton instance; private Singleton (){} public static Singleton getInstance() { if (instance == null) { instance = new Singleton(); } return instance; } }

Las siguientes formas de implementación admiten múltiples hilos, pero difieren en rendimiento.

2. Estilo perezoso, seguro para hilos

¿Inicialización Lazy?:Sí

¿Es seguro para hilos?:Sí

Dificultad de implementación:fácil

Descripción:Este enfoque tiene una muy buena carga diferida (lazy loading) y puede funcionar bien en entornos multihilo; sin embargo, la eficiencia es muy baja y en el 99% de los casos no se necesita sincronización.
Ventaja: solo se inicializa en la primera llamada, evitando desperdicio de memoria.
Desventaja: es necesario usar synchronized para garantizar el singleton, pero el bloqueo afecta la eficiencia.
El rendimiento de getInstance() no es crítico para la aplicación (este método no se usa con mucha frecuencia).

Ejemplo

public class Singleton { private static Singleton instance; private Singleton (){} public static synchronized Singleton getInstance() { if (instance == null) { instance = new Singleton(); } return instance; } }

3. Estilo ansioso

¿Inicialización Lazy?:no

¿Es seguro para hilos?:Sí

Dificultad de implementación:fácil

Descripción:Este enfoque es bastante común, pero es fácil que se generen objetos basura.
Ventaja: no hay bloqueo, por lo que la eficiencia de ejecución mejora.
Desventaja: se inicializa al cargar la clase, desperdiciando memoria.
Se basa en el mecanismo del classloader para evitar el problema de sincronización de múltiples hilos. Sin embargo, instance se instancia en el momento de la carga de la clase. Aunque hay muchas causas que provocan la carga de la clase, en el patrón Singleton la mayoría se debe a la llamada al método getInstance(), pero no se puede descartar que existan otras formas (u otros métodos estáticos) que causen la carga de la clase. En ese caso, inicializar instance claramente no logra el efecto de lazy loading.

Ejemplo

public class Singleton { private static Singleton instance = new Singleton(); private Singleton (){} public static Singleton getInstance() { return instance; } }

4. Doble verificación de bloqueo / Bloqueo de doble comprobación (DCL, es decir, double-checked locking)

Versión de JDK:A partir de JDK 1.5

¿Inicialización Lazy?:Sí

¿Es seguro para hilos?:Sí

Dificultad de implementación:Relativamente compleja

Descripción:Este enfoque utiliza un mecanismo de doble bloqueo, es seguro y mantiene un alto rendimiento en entornos multihilo.
El rendimiento de getInstance() es crítico para la aplicación.

Ejemplo

public class Singleton { private volatile static Singleton singleton; private Singleton (){} public static Singleton getSingleton() { if (singleton == null) { synchronized (Singleton.class) { if (singleton == null) { singleton = new Singleton(); } } } return singleton; } }

5. Estilo de registro / clase interna estática

¿Inicialización Lazy?:Sí

¿Es seguro para hilos?:Sí

Dificultad de implementación:General

Descripción:Este enfoque puede lograr el mismo efecto que el bloqueo de doble verificación, pero es más sencillo de implementar. Para la inicialización diferida de campos estáticos, se debe usar este enfoque en lugar del bloqueo de doble verificación. Este enfoque solo es adecuado para campos estáticos; el bloqueo de doble verificación se puede usar cuando se necesita inicialización diferida en campos de instancia.
Este enfoque también utiliza el mecanismo del classloader para garantizar que solo haya un hilo al inicializar instance. La diferencia con el tercer enfoque es que, en el tercer enfoque, en cuanto la clase Singleton se carga, instance se instancia (no logra el efecto de lazy loading); en este enfoque, aunque la clase Singleton se cargue, instance no necesariamente se inicializa. Esto se debe a que la clase SingletonHolder no se usa activamente; solo cuando se llama explícitamente al método getInstance se carga explícitamente la clase SingletonHolder, y así se instancia instance. Imagina que instanciar instance consume muchos recursos, por lo que quieres que se cargue de forma diferida; por otro lado, no deseas instanciarlo cuando se carga la clase Singleton, porque no puedes asegurar que la clase Singleton no sea cargada por ser utilizada activamente en otros lugares; en ese momento, instanciar instance obviamente no es apropiado. Por tanto, este enfoque resulta más razonable que el tercero.

Ejemplo

public class Singleton { private static class SingletonHolder { private static final Singleton INSTANCE = new Singleton(); } private Singleton (){} public static final Singleton getInstance() { return SingletonHolder.INSTANCE; } }

6. Enumeración

Versión JDK:Desde JDK1.5

Inicialización Lazy:no

Seguridad de subprocesos:Sí

Dificultad de implementación:fácil

Descripción:Esta implementación todavía no es ampliamente adoptada, pero es la mejor manera de implementar el patrón singleton. Es más concisa, admite automáticamente el mecanismo de serialización y previene absolutamente la múltiple instanciación.
Este enfoque es el que propugna Josh Bloch, autor de Effective Java. No solo evita los problemas de sincronización entre múltiples hilos, sino que también admite automáticamente el mecanismo de serialización, evita que la deserialización cree nuevos objetos y previene absolutamente la múltiple instanciación. Sin embargo, dado que la característica enum solo se agregó después de JDK1.5, escribir de esta manera puede resultar poco familiar y en la práctica laboral se usa raramente.
No se puede invocar el constructor privado mediante un ataque de reflexión (reflection attack).

Ejemplo

public enum Singleton { INSTANCE; public void whateverMethod() { } }

Consejo de experiencia:En general, no se recomienda usar los modos perezosos 1 y 2; se recomienda usar el modo ansioso 3. Solo cuando se necesita implementar explícitamente el efecto de lazy loading se usa el modo registrado 5. Si se trata de crear objetos mediante deserialización, se puede probar el modo enumeración 6. Si hay otros requisitos especiales, se puede considerar el modo de bloqueo de doble verificación 4.
