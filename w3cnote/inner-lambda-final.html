¿Por qué las clases internas locales y las clases internas anónimas solo pueden acceder a variables locales final?

Categoría Tecnología de programación

Recientemente, al mirar las clases internas, tenía una duda: las clases internas locales y las clases internas anónimas solo pueden acceder a variables locales final. Después de leer varios blogs, entendí mucho más.

Primero, veamos un ejemplo de una clase interna local:

Ejemplo

class OutClass {
        private int age = 12;
 
        public void outPrint(final int x) {
                class InClass {
                        public void InPrint() {
                                System.out.println(x);
                                System.out.println(age);
                        }
                }
                new InClass().InPrint();
        }
}

Aquí hay una clase externa OuterClass y una clase interna InClass. La clase interna accede a una variable local x de un método de la clase externa. Aquí, x debe ser final, de lo contrario se produce un error:

Cannot refer to a non-final variable x inside an inner class defined in a different method

A continuación, analicemos este problema:

La causa fundamental es el ciclo de vida de las variables en el ámbito de acción;

Primero hay que saber que: la clase interna y la clase externa están al mismo nivel; la clase interna no se destruye cuando el método termina de ejecutarse solo porque esté definida en un método.

Aquí surge el problema: cuando el método de la clase externa termina, la variable local se destruye, pero el objeto de la clase interna puede seguir existiendo (solo muere cuando ya nadie lo referencia). Aquí aparece una contradicción: el objeto de la clase interna accede a una variable inexistente. Para resolver este problema, se copia la variable local como variable miembro de la clase interna. De esta manera, cuando la variable local muere, la clase interna aún puede acceder a ella; en realidad, lo que se accede es una "copia" de la variable local. Así parece extenderse el ciclo de vida de la variable local. Podemos comprobarlo mediante la descompilación del archivo .class generado:

En la ventana de línea de comandos, primero ejecute el comandojavac OutClass.javapara compilar, se obtendrán dos archivos: OutClass$1InClass.class, OutClass.class:

javap es el desensamblador de archivos .class de Java; puede descompilar y también ver el bytecode generado por el compilador de Java.

Aquí podemos ejecutar nuevamente el comandojavap -privateOutClass$1InClasspara descompilar,-privateindica que se muestran todas las clases y miembros; después de ejecutarlo, se obtiene el siguiente resultado:

Se puede ver que la variable local en el método efectivamente se copia para usarse como variable miembro de la clase interna.

Pero aparece otro problema: al copiar la variable local como variable miembro de la clase interna, se debe garantizar que estas dos variables sean iguales. Es decir, si modificamos la variable miembro dentro de la clase interna, la variable local del método también debe cambiar. ¿Cómo resolver el problema?

Simplemente se define la variable local como final; después de inicializarla, no se permite modificarla, lo que garantiza la consistencia entre la variable miembro de la clase interna y la variable local del método. En realidad, esto es un compromiso.

Si la variable es final:

  • Si es de tipo primitivo, su valor no puede cambiar, lo que garantiza que la copia y el valor de la variable local original sean iguales;

  • Si es de tipo referencia, su referencia no puede cambiar, lo que garantiza que la copia y la variable original referencien al mismo objeto.

Esto mantiene la consistencia entre la variable local y la copia creada dentro de la clase interna.
