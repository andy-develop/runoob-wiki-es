Introducción a varios protocolos de código abierto

Clasificación Tecnología de programación

En el mundo existen alrededor de cien tipos de licencias de código abierto (Open Source License). Hoy presentaremos algunos de los protocolos de código abierto más comunes. Principalmente GPL, BSD, MIT, Mozilla, Apache, LGPL, etc.

Apache License

La Licencia Apache (Apache License) es una licencia de software libre publicada por la Apache Software Foundation.

La Licencia Apache es el protocolo adoptado por Apache, la famosa organización de código abierto sin fines de lucro. Este protocolo es similar a BSD, también fomenta el intercambio de código y los derechos de autor del creador original, y también permite la modificación y redistribución del código fuente. Sin embargo, también deben cumplirse las siguientes condiciones:

  • Es necesario proporcionar a los usuarios del código una copia de la Licencia Apache.
  • Si se modifica el código, se debe indicar en los archivos modificados.
  • En el código derivado (modificado o derivado del código fuente original) se debe incluir el protocolo, la marca comercial, las declaraciones de patentes y otras indicaciones que el autor original haya establecido que deben incluirse.
  • Si el producto redistribuido incluye un archivo Notice, el archivo Notice debe contener la Licencia Apache. Puede agregar sus propias licencias en el Notice, pero no puede parecer que modifica la Licencia Apache.
  • La Licencia Apache también es una licencia amigable para aplicaciones comerciales. Los usuarios también pueden modificar el código cuando sea necesario para satisfacer sus necesidades y publicarlo o venderlo como producto de código abierto o comercial.

Las ventajas de usar este protocolo son:

  • Derechos permanentes: una vez otorgados, se poseen de por vida.

  • Derechos a nivel mundial: si se obtiene la autorización en un país, aplica a todos los países. Por ejemplo, si estás en Estados Unidos y la licencia se otorga desde India, no hay problema.

  • Licencia gratuita: sin regalías, sin cargos iniciales ni posteriores.

  • Licencia no exclusiva: cualquier persona puede obtener la licencia.

  • Licencia irrevocable: una vez obtenida, nadie puede cancelarla. Por ejemplo, si desarrollas productos derivados basados en el código del producto, no tienes que preocuparte de que algún día se te prohíba usar ese código.

BSD

BSD es la abreviatura de "Berkeley Software Distribution", que significa "Distribución de Software de Berkeley".

El protocolo de código abierto BSD: es un protocolo que otorga gran libertad al usuario. Se puede usar y modificar el código fuente libremente, y también se puede redistribuir el código modificado como software de código abierto o propietario. Cuando publicas código que usa el protocolo BSD, o desarrollas tu propio producto basado en código con protocolo BSD, debes cumplir tres condiciones:

  • 1. Si el producto redistribuido incluye código fuente, el código fuente debe incluir el protocolo BSD del código original.
  • 2. Si lo que se redistribuye son solo bibliotecas binarias o software, entonces la documentación y los avisos de derechos de autor de la biblioteca o software deben incluir el protocolo BSD del código original.
  • 3. No se puede utilizar el nombre del autor u organización del código abierto ni el nombre del producto original para promoción comercial.

El código BSD fomenta el intercambio de código, pero requiere respetar los derechos de autor del autor del código. Debido a que BSD permite a los usuarios modificar y redistribuir el código, y también permite usar o desarrollar software comercial sobre código BSD para publicarlo y venderlo, es un protocolo muy amigable para la integración comercial. Muchas empresas eligen el protocolo BSD al seleccionar productos de código abierto, porque pueden controlar completamente estos códigos de terceros y modificarlos o realizar un desarrollo secundario cuando sea necesario.

GPL

GPL (GNU General Public License): Licencia Pública General de GNU.

Linux utiliza GPL.。

El protocolo GPL es muy diferente de licencias como BSD y Apache Licence que fomentan la reutilización del código. El punto de partida de GPL es el uso de código abierto o gratuito y el uso de código abierto o gratuito para referenciar, modificar o derivar, pero no permite que el código modificado y derivado se publique y venda como software comercial de código cerrado. Esta es la razón por la que podemos usar varios Linux gratis, incluidos los Linux de empresas comerciales y el software gratuito desarrollado por individuos, organizaciones y empresas de software comercial en Linux.

LGPL

LGPL es un protocolo de código abierto diseñado principalmente para uso en bibliotecas de clases, derivado de GPL. A diferencia de GPL, que exige que cualquier software que use, modifique o derive de bibliotecas GPL debe adoptar el protocolo GPL, LGPL permite que el software comercial use bibliotecas LGPL mediante referencia (enlace) sin necesidad de abrir el código del software comercial. Esto permite que el código abierto bajo protocolo LGPL sea referenciado como biblioteca de clases por software comercial, publicado y vendido.

Pero si se modifica o deriva código bajo protocolo LGPL, todo el código modificado, el código adicional relacionado con las partes modificadas y el código derivado deben adoptar el protocolo LGPL. Por lo tanto, el código abierto bajo protocolo LGPL es muy adecuado para ser referenciado como biblioteca de terceros por software comercial, pero no es adecuado para software comercial que desee realizar un desarrollo secundario basado en código LGPL mediante modificación y derivación.

Tanto GPL como LGPL protegen los derechos de propiedad intelectual del autor original, evitando que alguien utilice el código abierto para copiar y desarrollar productos similares.

MIT

MIT es una licencia tan amplia como BSD, originada en el Instituto de Tecnología de Massachusetts (Massachusetts Institute of Technology, MIT), también conocida como protocolo X11. El autor solo desea conservar los derechos de autor, sin ninguna otra restricción. MIT es similar a BSD, pero más permisivo que BSD, siendo actualmente el protocolo con menos restricciones. La única condición de este protocolo es que el código modificado o el paquete de distribución incluya la información de licencia del autor original. Es adecuado para software comercial. Proyectos de software que usan MIT: jquery, Node.js.

MPL (Mozilla Public License 1.1)

El protocolo MPL permite la redistribución gratuita y la modificación gratuita, pero exige que los derechos de autor del código modificado pertenezcan al iniciador del software. Esta licencia protege los intereses del software comercial, ya que requiere que las modificaciones basadas en este software contribuyan gratuitamente los derechos de autor a dicho software. Así, los derechos de autor de todo el código alrededor del software se concentran en manos del desarrollador iniciador. Sin embargo, MPL permite la modificación y el uso gratuito. El software MPL no tiene requisitos sobre enlaces.

EPL (Eclipse Public License 1.0)

EPL permite a los destinatarios usar, copiar, distribuir, difundir, mostrar, modificar y realizar publicaciones comerciales secundarias de código cerrado después de la modificación.

Al usar el protocolo EPL, se deben seguir las siguientes reglas:

  • Cuando un Contribuyente publica nuevamente el código fuente total o parcialmente como código abierto, debe continuar publicándolo bajo el protocolo de código abierto EPL, y no puede cambiarlo a otro protocolo, a menos que obtenga la autorización del propietario del "código fuente" original.
  • Bajo el protocolo EPL, puedes publicar comercialmente el código fuente sin realizar ninguna modificación. Pero si vas a publicar el código fuente modificado, o cuando redistribuyes Código Objeto, debes declarar que su Código Fuente está disponible e indicar el método para obtenerlo.
  • Cuando necesites mezclar el código fuente bajo EPL como parte de un Proyecto con otro código fuente privado para publicarlo, puedes publicar todo el Proyecto o Producto bajo un protocolo privado, pero debes declarar qué parte del código está bajo EPL y declarar que esa parte continúa siguiendo EPL.

Creative Commons: acuerdo de conocimiento compartido

Las licencias Creative Commons (CC) no pueden considerarse verdaderos protocolos de código abierto; en su mayoría se utilizan en proyectos de diseño. Hay muchos tipos de protocolos CC, y cada uno otorga derechos específicos. Una licencia CC tiene cuatro partes básicas, que pueden funcionar individualmente o combinarse. A continuación se presenta una breve introducción a estas partes:

  • 1. Atribución: La obra debe llevar la atribución correspondiente. Después de esto, la obra puede ser modificada, distribuida, copiada y utilizada para otros fines.
  • 2. Compartir igual: La obra puede ser modificada, distribuida o sometida a otras operaciones, pero todos los derivados deben estar bajo la licencia CC.
  • 3. Uso no comercial: La obra puede ser modificada, distribuida, etc., pero no puede usarse con fines comerciales. Sin embargo, la explicación de qué es "comercial" es bastante ambigua (no se proporciona una definición precisa), por lo que puedes aclararlo en tu proyecto. Por ejemplo, algunos interpretan simplemente "no comercial" como que no se puede vender la obra. Otros consideran que ni siquiera se puede usar en sitios web con publicidad. Algunos piensan que "comercial" solo se refiere a obtener ganancias con ella.
  • 4. Sin obras derivadas

Estos términos de la licencia CC se pueden combinar libremente. La mayoría de los protocolos CC más estrictos declaran las cláusulas "Atribución, Uso no comercial, Sin derivados", lo que significa que puedes compartir libremente la obra, pero no puedes modificarla ni cobrar por ella, y debes indicar la atribución de la obra. Esta licencia es muy útil, ya que permite difundir tu obra mientras se mantiene un control parcial o total sobre su uso. El tipo de protocolo CC menos restrictivo es el de "Atribución", lo que significa que mientras las personas mantengan tu reputación, pueden usar tu obra como quieran.

Las licencias CC se utilizan más en proyectos de diseño que en proyectos de desarrollo, pero nada impide que las uses en estos últimos. Solo debes tener claro los derechos que cada cláusula cubre y los que no cubre.
