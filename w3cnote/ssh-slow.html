Explicación detallada de las soluciones para la lentitud de la conexión SSH

分类 编程技术

Cada vez que uso PuTTY para iniciar sesión vía SSH en un Linux remoto para administrarlo, el proceso de inicio de sesión remoto es muy lento: después de ingresar el nombre de usuario, hay que esperar unos 30 segundos para que aparezca el indicador de contraseña. Al abordar problemas reales, especialmente cuando se necesita una respuesta rápida, esta situación resulta realmente insoportable.

Pero luego hice pruebas concretas y descubrí que esto no es un problema común en todos los sistemas. Las máquinas con problemas se concentran principalmente en CentOS. En el mismo sistema Debian, el proceso de conexión remota es rápido como el viento, sin la más mínima sensación de retraso o titubeo. ¿Será un problema de CentOS?

Por curiosidad, revisé las diferencias entre los dos sistemas al usar SSH.

¿Existen otros métodos además de este? Por supuesto que los hay. CentOS ya nos ofrece una solución: deshabilitar la autenticación GSSAPI al usar SSH para el inicio de sesión remoto. Eso sí, hay otro problema que no se puede ignorar: si en tu máquina está habilitado UseDNS, también debes desactivarlo; para más detalles, consulta la explicación al final.

A partir del error se puede ver que es un problema relacionado con el dominio del host: probablemente no se puede confirmar el dominio correspondiente a la IP, y por eso aparece este problema. GSSAPI se basa principalmente en Kerberos, por lo que resolver este problema requeriría tener Kerberos configurado en el sistema. Para aquellos que no tienen Kerberos, configurar Kerberos solo para resolver un problema de retraso en el inicio de sesión no parece una decisión sensata, especialmente en entornos de producción. ¡Satisfacer las necesidades con la mínima configuración es lo primordial!

A continuación, primero presento el método para manejar GSSAPI.

Hay dos formas de deshabilitar la autenticación GSSAPI: en el cliente y en el servidor.

1. Deshabilitar en el cliente

Es relativamente simple y solo afecta a un único cliente; se puede implementar con el siguiente método:

ssh -o GSSAPIAuthentication=no your-server-username@serverIP

Con el método anterior para iniciar sesión remota, se puede lograr deshabilitar GSSAPIAuthentication.

Si te parece engorroso, configura directamente el archivo /etc/ssh/ssh_config de tu cliente SSH para resolver este problema de forma permanente:

vi /etc/ssh/ssh_config
### 找到ssh_config文件里面的GSSAPIAuthentication yes这行
### 修改为GSSAPIAuthentication no
### 保存ssh_config文件并退出

Este método de modificación afecta a todos los usuarios de esta máquina. Si no quieres que el impacto sea tan amplio y solo deseas deshabilitar GSSAPIAuthentication para un usuario específico, puedes ir al directorio de ese usuario, buscar el directorio .ssh, añadir un archivo config debajo y agregar la línea anterior en el archivo. Si el archivo no existe, también puedes hacerlo directamente:

cat >>~/.ssh/config<<EOF
GSSAPIAuthentication no
EOF

Usa cat para exportar la entrada directamente al archivo. En ese momento, cuando uses SSH para conectarte al host remoto, ya no usarás la autenticación GSSAPI.

Los archivos anteriores están en el cliente, no en el servidor. Es decir, para modificar este archivo, tu cliente también debe ser Linux.

Si estás en Windows y usas herramientas de cliente como PuTTY, no uses el método anterior. En PuTTY puedes intentar configurarlo antes de la conexión:

PuTTY Configuration -> Connection -> SSH -> Auth -> GSSAPI -> (取消勾选)Attempt GSSAPI authentication(SSH-2 only)

Si no has deshabilitado GSSAPIAuthentication en PuTTY, puedes hacer clic derecho en la ventana de conexión (o Ctrl + clic derecho) para ver el registro. Podrás encontrar registros en los que PuTTY intenta automáticamente una conexión GSSAPI:

2014-05-18 23:46:54 Using SSPI from SECUR32.DLL
2014-05-18 23:46:54 Attempting GSSAPI authentication
2014-05-18 23:46:54 GSSAPI authentication request refused

Bueno, lo anterior básicamente enumera los métodos para deshabilitar GSSAPIAuthentication en el cliente.

Nota: los métodos anteriores son bastante generales.

2. Si ya has configurado Kerberos

Entonces también puedes probar el siguiente método para resolver este problema en el cliente:

Agrega el nombre de host del host remoto al archivo hosts de tu máquina local (en Linux es /etc/hosts, en Windows es disco del sistema:/Windows/System32/drivers/etc/hosts). Tanto en Linux como en Windows puedes agregar la siguiente línea.

### 注意：下面这样的IP-Addr要替换成你的远程机器的IP地址，HostName，自然是主机名
IP-Addr HostName

Después de añadirlo, guarda y sal.

3、服务端禁用GSSAPIAuthentication。

Ve directamente a /etc/ssh/sshd_config y cambia GSSAPIAuthentication yes a no. También ten en cuenta que quizás debas cambiar UseDNS a UseDNS no (ojo, el valor predeterminado varía según el sistema; aquí se usa CentOS 6 como ejemplo):

sudo vi /etc/ssh/sshd_config
### 普通用户权限不够，需要root权限
### 找到GSSAPIAuthentication yes，修改为
### GSSAPIAuthentication no
### 注意，这里你也需要将UseDNS修改为no，CentOS默认是yes，即使这行已被注释，你也需要加上
### UseDNS no
### 有看到人说UseDNS yes不需要修改为UseDNS no，Mitchell测试下来是需要的。
### 保存文件，退出

Una vez deshabilitado, debemos reiniciar el servicio SSH para garantizar que el nuevo archivo de configuración se aplique correctamente:

service sshd restart

En este momento, al usar SSH para iniciar sesión nuevamente en este host, ¿no sientes que es rapidísimo?

说明

1. GSSAPI: Generic Security Services Application Program Interface. GSSAPI en sí es un conjunto de APIs, estandarizado por la IETF. Su implementación más importante y famosa se basa en Kerberos. Generalmente, cuando se menciona GSSAPI, se hace referencia implícita a la implementación de Kerberos.

2. UseDNS: es una opción de búsqueda DNS en el servidor OpenSSH, y está activada por defecto. Cuando está activada, cada vez que un cliente intenta conectarse al servidor OpenSSH, el servidor realiza automáticamente una búsqueda inversa PTR de DNS según la IP del cliente (solo habrá registro si se ha hecho la resolución inversa de IP), obtiene el Hostname correspondiente a la IP y luego realiza una búsqueda directa de registro A de DNS según el Hostname del cliente. Mediante esta consulta, verifica si la IP coincide con la IP del cliente conectado. Pero en la gran mayoría de nuestros equipos la IP se obtiene dinámicamente, es decir, esta opción no sirve en absoluto para este caso. Incluso para servidores con IP estática normal, mientras no se haya realizado la resolución inversa de IP, difícilmente es aplicable. Si cumples estas condiciones, se recomienda desactivar UseDNS para aumentar la velocidad de autenticación al iniciar sesión remota por SSH.
