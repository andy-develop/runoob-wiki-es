0.3 Especificaciones de código Verilog

Categoría Tutorial de Verilog - Nivel avanzado

De casualidad vi un diseño FPGA que escribí hace varios años. El estilo del código era más o menos aceptable, pero los riesgos ocultos en el diseño lógico eran omnipresentes. Muchos principiantes escriben código Verilog básicamente siguiendo el pensamiento y el estilo del lenguaje C, lo que causa muchos problemas comunes no estándar.

Esta sección resume principalmente algunos diseños Verilog no estándar y peligrosos. Se centra principalmente en diseños digitales sintetizables; el testbench es un programa de simulación y, en general, los requisitos no son muy estrictos.

El contenido de las especificaciones de código es diferente del estilo de codificación. El estilo de codificación es solo una sugerencia; el diseñador puede no seguir las sugerencias de estilo de codificación de este tutorial y escribir código libremente. Siempre que la lógica sea correcta y el circuito sea seguro, incluso si se escribe con un estilo desordenado, con tal de que el compilador pueda compilar y simular correctamente, está bien. El diseñador puede decir con orgullo: ¡escribe tu propio código y que otros lo adivinen!

Las especificaciones de código son reglas que deben seguirse hasta cierto punto; de lo contrario, pueden afectar la corrección de la lógica del circuito digital. A menos que se trate de un diseño especial, o que la persona sea muy experimentada y esté completamente segura, y pueda exceder ligeramente las especificaciones de código Verilog, se recomienda prestar atención a estas reglas en el diseño. Especialmente los principiantes son propensos a violar estos problemas.

Sobre la asignación de valores iniciales

No asigne valores iniciales a las variables al declararlas. Si se establece un valor inicial en la declaración de la variable, la variable tendrá el valor inicial esperado durante la simulación, pero el valor inicial del circuito después de la síntesis es incierto. Si el valor inicial de la señal afecta la funcionalidad lógica, el proceso de simulación puede perder la oportunidad de detectar errores lógicos debido a una verificación insuficiente. Por ejemplo, la siguiente descripción no es recomendable:

    reg [31:0]      wdata = 32'b0 ;

La operación de asignación de valores iniciales debe realizarse en estado de reinicio (reset). También se recomienda que las variables de registro utilicen un puerto de reset para garantizar que, cuando el sistema se encienda o se desordene, se pueda restaurar al estado inicial mediante una operación de reset.

Se recomienda que, en el diseño, el reloj use lógica de flanco positivo y el reset use lógica de flanco negativo. Para el diseño de reset, consulte«5.1 Introducción al reset»。

Durante el reset, todas las señales en el bloque de sentencias deben recibir valores iniciales; no omita señales relevantes.

    always @(posedge clk or negedge rstn) begin
        if (!rstn) begin
            cnt  <= 'b0 ; //Omitir la asignación del valor inicial a cout es muy peligroso
        end
        else if (cnt == 10) begin
            cnt  <= 4'b0 ;
            cout <= 1'b1 ;
        end
        else begin
            cnt  <= cnt + 1'b1 ;
            cout <= 1'b0 ;
        end
    end

Sobre la sentencia always

A menos que sea absolutamente necesario, no utilice lógica de flanco ascendente y descendente del mismo reloj en dos bloques always separados; de lo contrario, se introducirán problemas relativamente complejos de calidad de reloj y restricciones de temporización.

   //Se recomienda evitar en lo posible la lógica de 2 bloques always con 2 flancos de reloj
   always @(posedge clk) begin
      a <= b ;
   end
   always @(negedge clk) begin
      c <= d ;
   end

Está prohibido utilizar ambos flancos del reloj como condición de disparo en un mismo bloque always. La compilación y la simulación pueden comportarse según lo que el diseñador espera, pero este tipo de circuito a menudo no es sintetizable, o la función del circuito después de la síntesis no cumplirá lo esperado.

   //Prohibido usar lógica de doble flanco en un bloque always
   always @(posedge clk or negedge clk) begin
      a <= b ;
   end  

Está prohibido asignar valores a la misma variable en dos bloques always. Este es un error común que muchos principiantes cometen fácilmente.

  //Este diseño es incorrecto
   always @(posedge clk) begin
      a <= b ;
   end
   always @(negedge clk) begin
      a <= d ;
   end

No debe haber múltiples sentencias condicionales paralelas o no relacionadas en un bloque always; utilice múltiples bloques always para describirlas por separado.

Cuando hay múltiples sentencias condicionales paralelas o no relacionadas en una sentencia always, tanto en los resultados de la simulación como en el circuito real sintetizado, las sentencias condicionales no relacionadas se ejecutan en paralelo. Sin embargo, el proceso de simulación puede ejecutarse secuencialmente; si hay información de retardo, puede provocar resultados erróneos impredecibles. Además, este estilo de escritura tiene poca legibilidad y la división funcional no es clara.

    //No recomendado
    always @(posedge clk) begin
        if (a == b)
            data_t1 <= data1 ;

        if (a == b && c == d)
            data_t2 <= data2 ;
        else
            data_t2 <= 'b0 ;
    end
   
    //Se recomienda escribirlas por separado
    always @(posedge clk) begin
        if (a == b)
            data_t1 <= data1 ;
    end
    always @(posedge clk) begin
        if (a == b && c == d)
            data_t2 <= data2 ;
        else
            data_t2 <= 'b0
    end

Sobre el reloj y la asincronía

En el diseño, intente utilizar diseño síncrono tanto como sea posible.

Cuando sea necesario utilizar lógica asíncrona, se debe realizar un procesamiento de sincronización de las señales entre diferentes dominios de reloj; no se pueden usar las señales directamente, de lo contrario se generarán circuitos metaestables. Para la implementación específica del procesamiento de sincronización, consulte«4.1 Síncrono y asíncrono»y los capítulos relacionados posteriores.

Intente no realizar operaciones lógicas directamente entre la señal de reloj y señales variables ordinarias, ni detectar o juzgar el nivel de la señal de reloj. Por ejemplo, las siguientes descripciones no son recomendables.

    assign clk_gate = clk & clken ;
    assign dout = (clk == 1'b1) ? din : 0 ;
    always @(posedge clk) begin
        if (clk = 1'b1)
            data_t1 <= data1 ;
    end    

Al seleccionar el reloj bajo diferentes condiciones, no se puede usar lógica de selección directamente, de lo contrario aparecerán glitches. Consulte«5.4 Conmutación del reloj»。

Sobre la síntesis

En general, las variables de señal no deben usar directamente multiplicación*división/módulo (resto)%y otras operaciones. Después de la síntesis, la estructura y la temporización de estos operadores suelen ser difíciles de controlar. Se deben utilizar módulos IP optimizados o módulos integrados de la biblioteca de tecnología. Sin embargo, las constantes de tipo parameter pueden usar este tipo de operadores, porque el compilador calcula el resultado de las operaciones con constantes al comienzo de la compilación, sin consumir recursos de hardware adicionales.

En las sentencias condicionales de lógica combinatoria, complete todas las condiciones; en las sentencias always de lógica combinatoria, enumere todas las señales sensibles para evitar la generación de Latch no deseado. Consulte«6.5 Verilog evitar Latch» del «Tutorial de Verilog»。

Al diseñar lógica, se debe considerar si el código se puede sintetizar en un circuito real y qué tipo de circuito resultará. Consulte«9.2 Diseño sintetizable»。

Sobre la instanciación

Al instanciar, las señales conectadas a los puertos de entrada pueden ser variables de tipo reg o wire, y las señales conectadas a los puertos de salida deben ser variables de tipo wire. Sin embargo, al declarar las señales de puerto, las señales de entrada deben ser variables de tipo wire, y las señales de salida pueden ser variables de tipo reg o wire.

Al instanciar múltiples módulos, el nombre del módulo va primero y el nombre de la instanciación va después; además, los nombres de instanciación no pueden ser iguales.
